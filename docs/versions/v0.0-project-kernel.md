# v0.0 Project Kernel

## 目标

建立整个插件的干净地基。这个版本不要急着变成写作工具，而是证明 LoreDock 可以通过模块持续扩展，不会变成一个纠缠在一起的巨大命令文件。

v0.0 的核心价值是降低后期“牵一发而动全身”的概率。它要先把模块边界、文件边界、schema 边界和写入边界立住。

## 实现

- 搭建 VS Code Extension + TypeScript 工程。
- 建立统一命令注册 helper，并带有一致的错误处理。
- 实现 `ProjectKernel`，负责 workspace 检测、项目根目录解析和激活状态。
- v0.0 项目根目录固定为目标 workspace folder，manifest 固定为 `<workspaceFolder>/.loredock/project.json`；不做向上搜索、向下搜索、递归搜索或嵌套项目识别。
- 明确 VS Code multi-root 策略：v0.0 默认支持单 workspace folder；打开多个 workspace folder 时，项目命令必须让用户显式选择目标 folder（QuickPick），并把 manifest、路径解析和诊断都绑定到该 folder。基于资源管理器文件、编辑器或命令参数的自动上下文推断不在 v0.0 范围内，留待后续版本。
- 创建 `.loredock/project.json`，包含 `schemaVersion`、`projectId`、`title`、`createdAt`、`updatedAt` 和启用的 capabilities。
- 定义 manifest 最小契约：字段类型、时间格式、capability 列表格式、缺字段处理、类型错误处理和 JSON 损坏处理。
- 实现 `SchemaRegistry`，管理版本化文档 schema；v0.0 先以内存/代码注册为主，不写 `.loredock/schemas/`。
- 实现 `MigrationRunner` 的基础接口，但 v1.0 前不承诺旧草稿项目兼容；v0.0 只支持 no-op 流程验证，不自动迁移未知版本。
- 实现 `SafeFileWriter`，使用同目录临时文件 + rename 的最小原子写入策略，并拒绝任何写出 workspace 的路径。
- 实现统一的 preview/apply 操作模型接口，并让 `loredock.initProject` 成为第一条最小 preview/apply 流程；后续导入、修复、AI 和同步都要复用这条路径。
- 定义 capability 注册接口：
  - commands
  - views
  - schemas
  - file watchers
  - diagnostics
- 定义 capability 生命周期：capability 通过 `activate(context)` 注册资源，并返回 disposables，由 Kernel 统一释放。
- 定义路径规则：所有模块只接收 workspace-relative path，不能保存绝对路径作为项目数据。
- 建立日志和诊断输出通道；v0.0 使用 VS Code OutputChannel 和内存 diagnostics，不把诊断结果作为 canon 写盘。
- 定义内存 diagnostics 的最小结构：`severity`、`code`、`message`、`workspaceFolder` 和可选 `relativePath`。
- 最小命令：
  - `loredock.initProject`
  - `loredock.openProjectManifest`
  - `loredock.showDiagnostics`
  - `loredock.repairProjectManifest`
- 建立测试 fixtures：空 workspace、已初始化 workspace、损坏 manifest。

## 干净与可扩展性约束

v0.0 的干净不是靠大量抽象，而是靠边界清楚。Kernel 只负责 workspace、manifest、schema、命令注册、诊断、安全写入和 preview/apply 操作模型，不理解任何具体写作业务。

Manifest 必须保持薄，只记录项目身份、版本和启用的 capabilities。手稿、资料库、时间线、导出等后续模块必须拥有自己的文件边界和 schema，不能把业务细节塞进 `.loredock/project.json`。

所有项目文件写入必须经过 `SafeFileWriter`。后续如果需要备份、原子写入、失败恢复、写入日志或预览确认，只能扩展统一写入层，不能让模块各自散落写文件逻辑。

所有复杂修改必须走 preview/apply 模型。导入、修复、同步、AI 建议、批量重命名和蓝图变更未来都复用同一条写入路径。

项目数据中只能保存 workspace-relative path，不能保存绝对路径。这样项目可以移动、复制、进入 Git，并且更容易被测试 fixture 覆盖。

workspace-relative path 必须经过统一解析和校验。normalize 后仍必须位于目标 workspace 内；绝对路径、`..` 逃逸、跨 workspace 写入，以及符号链接导致的项目外写入都必须被拒绝。对尚未存在的目标文件，要校验目标父目录的 realpath；新建路径的每个已存在父级都必须确认真实路径仍在目标 workspace 内。已有目标文件如果是 symlink，必须校验其 realpath；指向 workspace 外则拒绝。

VS Code multi-root 必须有明确目标。v0.0 默认支持单 workspace folder；当存在多个 workspace folder 时，初始化、打开 manifest、显示诊断、修复 manifest 等项目命令必须让用户显式选择目标 workspace folder，不能隐式选择第一个 workspace。基于资源管理器文件、编辑器文件或命令参数的自动上下文推断推迟到后续版本，不在 v0.0 实现。

项目根目录必须固定。v0.0 不识别嵌套 LoreDock 项目，不从当前文件向上搜索 `.loredock/project.json`，也不扫描 workspace 子目录；目标 workspace folder 就是项目根。

未打开 workspace 时必须安全退出。`loredock.initProject`、`loredock.openProjectManifest`、`loredock.showDiagnostics` 和 `loredock.repairProjectManifest` 都不能写文件，只显示友好提示，并把原因写入 OutputChannel。

Manifest 最小契约必须清楚。`schemaVersion` 使用字符串，`projectId` 由 Kernel 生成并保持稳定，`title` 是项目标题，`createdAt` 和 `updatedAt` 使用 ISO 时间字符串，`capabilities` 是已启用 capability id 列表。JSON 损坏、缺字段和字段类型错误都进入 diagnostics，不能让插件激活崩溃。

`capabilities` 必须是字符串数组。非字符串、空字符串和空白字符串是 validation error；重复 capability id 进入 diagnostics，激活时可以在内存中去重，但不能为了去重静默改写 manifest。

v0.0 只正式支持 `schemaVersion: "0.0.0"`。空字符串、非字符串、未知版本和未来版本都进入 diagnostics + degraded mode；`MigrationRunner` 在 v0.0 只验证 no-op 流程，不自动改写或迁移未知版本 manifest。

初始 manifest 必须有固定默认值。`schemaVersion` 初始为 `0.0.0`，`projectId` 使用 Kernel 生成的稳定 ID，`title` 默认取 workspace folder 名称，`createdAt` 和 `updatedAt` 在初始化时相同，`capabilities` 初始为空数组。

`projectId` 生成规则必须固定。v0.0 使用 `loredock_` 前缀加 UUID/random ID；初始化后不会因为 workspace 路径、folder 名称或 `title` 变化而改变。validation 接受非空字符串，生成的新 ID 必须使用该前缀。

最小 manifest 示例：

```json
{
  "schemaVersion": "0.0.0",
  "projectId": "loredock_...",
  "title": "My Novel",
  "createdAt": "2026-06-29T00:00:00.000Z",
  "updatedAt": "2026-06-29T00:00:00.000Z",
  "capabilities": []
}
```

`updatedAt` 只在 manifest 自身被 Kernel 写入或修复时更新。读取 manifest、打开 manifest、生成 diagnostics 或显示 diagnostics 都不能更新 `updatedAt`，避免无意义的文件 churn。

Manifest 无法解析或 validation 失败时，Kernel 进入 degraded mode。degraded mode 只启用诊断、打开 manifest、初始化和修复相关命令，不激活 feature capabilities。由于已有 manifest 时 `initProject` 会被阻止，degraded mode 下修复损坏 manifest 的正式入口是 `loredock.repairProjectManifest`；诊断和提示应引导用户走修复，而不是重新初始化。

损坏 manifest 的恢复必须显式执行。`loredock.repairProjectManifest` 通过 preview/apply 运行：preview 展示将备份当前损坏 manifest 并写入新的最小 manifest；apply 先把旧文件备份到同目录带时间戳的 `.bak` 文件，再写入新的最小 manifest；verify 重新读取并校验 manifest。修复命令不能静默覆盖原文件。manifest 不存在时，`loredock.repairProjectManifest` 不创建文件，只提示用户先运行 `loredock.initProject`，并把原因写入 OutputChannel。

修复时必须尽量保留项目身份。manifest JSON 可解析时，合法的 `projectId`、`title`、`createdAt` 和 `capabilities` 要优先保留（合法与未知 capability id 都保留，不静默删除，与正常激活时的处理一致），`updatedAt` 更新为修复时间；完全无法解析或字段非法时，才生成新的 `projectId`、使用 workspace folder 名称作为 `title`，使用修复时间作为 `createdAt` 和 `updatedAt`，并把 `capabilities` 重置为空数组。

修复未来版本 manifest 必须有明确警告。如果 manifest 可解析但 `schemaVersion` 是未知或未来版本，`loredock.repairProjectManifest` 的 preview 必须说明这是重建 v0.0 manifest，不是 migration；用户取消时不能写入任何文件。

SchemaRegistry 在 v0.0 只提供代码内注册和查询能力，不落盘 schema 文件，也不创建 `.loredock/schemas/`。后续需要项目级 schema 包时，再由对应版本定义写盘格式。

后续能力只能通过 Capability API 挂载。新增模块可以注册 commands、views、schemas、file watchers 和 diagnostics，但不能直接调用 Kernel 私有实现，也不能直接调用其他 capability 的私有实现。

Manifest 中出现当前插件不认识的 capability id 时，不能阻止项目打开。Kernel 只激活当前已注册且在 manifest 中启用的 capability，未知 capability 进入 diagnostics，保留在 manifest 中，不能被静默删除。

Capability 必须有可释放的生命周期。每个 capability 通过 `activate(context)` 注册资源并返回 disposables；Kernel 统一负责释放，测试必须能证明示例 capability 可以注册和卸载。

示例空 capability 只用于代码层测试 Capability API，不默认写入用户 manifest。测试可以使用 fixture manifest 显式启用 `example.empty`，验证它可以注册和卸载。

重复初始化必须保守处理。已有 manifest 时默认阻止重复初始化；用户显式确认后，`initProject` 只允许打开现有 manifest 或补齐 v0.0 所需的最小目录（`.loredock/`），绝不改写或覆盖 `.loredock/project.json`。在 v0.0 命令范围内，改写 manifest 内容只能通过 `loredock.repairProjectManifest`（带备份）执行；后续版本启用 capability 等对 manifest 的写入必须经各自的 preview/apply 命令和统一写入层完成，同样不得静默覆盖。

v0.0 初始化范围必须保持最小。`initProject` 只保证 `.loredock/` 和 `.loredock/project.json`；`schemas/`、`indexes/`、`snapshots/`、`diagnostics/`、手稿目录、资料目录和导出目录等，等对应 capability 或版本真正需要时再创建。

`SafeFileWriter` 的原子写入语义必须固定：临时文件写在目标文件同目录，校验成功后用 rename 替换目标文件；失败时尽力清理临时文件；只允许创建 preview/apply 中已经声明的目录。这里的校验只包含路径安全、operation plan 范围和临时文件写入结果，不包含业务 schema validation。

preview/apply 的最小 operation plan 必须可检查。v0.0 至少包含 `summary`、`directoriesToCreate`、`filesToCreate` 和 `filesToModify`，apply 阶段只能执行 plan 中声明过的文件和目录变化。

preview/apply 的 v0.0 确认 UI 必须保持简单。preview 阶段把 operation plan 摘要打印到 LoreDock OutputChannel，并用 VS Code modal message 或 QuickPick 提供 `Apply` / `Cancel`；用户取消或关闭确认时，apply 不执行，不能写入任何文件。

`loredock.repairProjectManifest` 的 operation plan 必须显式声明备份文件和 manifest 写入。备份 `.bak` 文件列入 `filesToCreate`，新的 `.loredock/project.json` 列入 `filesToModify`；如果备份文件名冲突，必须生成新的带时间戳或序号的备份名并重新进入 preview。

`loredock.showDiagnostics` 的 v0.0 行为必须简单明确：打开 LoreDock OutputChannel，并把当前内存 diagnostics 重新打印一次；不创建 webview、虚拟文档或磁盘诊断文件。

`loredock.openProjectManifest` 的 v0.0 行为必须保守。manifest 存在时打开 `<workspaceFolder>/.loredock/project.json`；manifest 不存在时不创建文件，只提示用户先运行 `loredock.initProject`，并把原因写入 OutputChannel。

diagnostics item 必须有稳定字段。v0.0 至少包含 `severity`、`code`、`message`、`workspaceFolder`，并可选包含 `relativePath`；`severity` 只允许 `info`、`warning` 或 `error`；`showDiagnostics` 按这些字段输出，方便测试断言。

diagnostics 必须在关键状态变化后刷新。插件激活、目标 workspace folder 切换、manifest 写入和 `loredock.repairProjectManifest` 完成后，都要重新读取 manifest 并运行 validation，避免 `showDiagnostics` 输出过期结果。

Kernel 内部不能 import 任何 feature module。`extension.ts` 可以作为 composition root 组装 capability 列表，但 Kernel 私有实现不能依赖具体业务模块。

## 优化

- 所有路径都使用 workspace-relative 表示。
- 集中管理错误信息，后续模块复用同一套用户提示风格。
- 文件 IO API 保持小而可测试。
- Kernel 阶段不引入无关依赖。
- Kernel 不能依赖 Manuscript、Story Bible、Timeline、Assistant、Blueprint 或 Compile。
- Capability 之间不能直接互相调用私有实现，必须通过公开 registry 或 projection。

## 打磨

- 清晰的首次使用提示。
- 未打开 workspace 时给出友好警告。
- README 说明项目结构和本地优先原则。
- 写一份内部架构说明，解释后续 capability 如何注册命令、视图和 schema。

## 验收标准

- 空 workspace 可以被初始化。
- 未打开 workspace 时，所有最小命令都不会写文件，只显示友好提示并写入 OutputChannel。
- 重复初始化会被阻止，除非用户显式确认。
- 损坏 manifest 会产生诊断，而不是导致插件激活崩溃。
- 测试覆盖项目检测、manifest 读写和 migration no-op。
- manifest 损坏或 validation 失败时进入 degraded mode，只启用诊断、打开 manifest、初始化和修复相关命令。
- 项目根固定为目标 workspace folder，manifest 固定为 `<workspaceFolder>/.loredock/project.json`，不做嵌套项目或递归搜索。
- multi-root workspace 中，项目命令必须让用户显式选择目标 folder（或接收明确的目标参数），不能隐式写入错误 workspace；自动上下文推断不在 v0.0 验收范围内。
- 路径校验会拒绝绝对路径、`..` 逃逸、跨 workspace 写入和符号链接逃逸；新建文件会校验已存在父级的 realpath，已有 symlink 目标文件会校验自身 realpath。
- manifest validation 覆盖合法 manifest、缺字段、类型错误和 JSON 损坏。
- `capabilities` validation 覆盖非数组、非字符串、空字符串、空白字符串和重复 id；重复 id 激活时内存去重但不改写 manifest。
- 只有 `schemaVersion: "0.0.0"` 被视为 v0.0 支持版本；未知或未来版本进入 diagnostics + degraded mode，不自动迁移。
- 初始 manifest 默认值固定：`schemaVersion` 为 `0.0.0`，`title` 取 workspace folder 名称，`capabilities` 为空数组。
- 新生成的 `projectId` 使用 `loredock_` 前缀加 UUID/random ID，并且不会因为 workspace 路径、folder 名称或 `title` 变化而改变。
- `loredock.repairProjectManifest` 可以通过 preview/apply 备份损坏 manifest，并写入新的最小 manifest；JSON 可解析时尽量保留合法的 `projectId`、`title`、`createdAt` 和 `capabilities`，`updatedAt` 更新为修复时间。
- `loredock.repairProjectManifest` 在 manifest 不存在时不会创建文件，只提示用户先运行 `loredock.initProject`。
- `loredock.repairProjectManifest` 遇到未知或未来版本 manifest 时，preview 必须明确提示这是重建 v0.0 manifest，不是 migration。
- SchemaRegistry 在 v0.0 不写 `.loredock/schemas/`，只验证代码内 schema 注册和查询。
- 未知 capability id 不阻止项目打开，会进入 diagnostics，并且不会被静默从 manifest 删除。
- `updatedAt` 只在 manifest 被写入或修复时变化；只读命令不会改变 manifest。
- `loredock.initProject` 走最小 preview/apply 流程：preview 生成包含 `summary`、`directoriesToCreate`、`filesToCreate` 和 `filesToModify` 的 operation plan，确认后 apply，写入后 verify，再 report。
- preview/apply 确认 UI 打印 operation plan 摘要，并提供 `Apply` / `Cancel`；取消或关闭确认不会写入任何文件。
- `loredock.initProject` 只创建 `.loredock/` 和 `.loredock/project.json`，不提前创建后续 capability 的目录。
- `loredock.repairProjectManifest` 的 operation plan 明确列出 `.bak` 备份文件和 `.loredock/project.json` 写入，备份文件名冲突时重新生成并重新 preview。
- 已存在 manifest 时不会被静默覆盖；用户确认后 `initProject` 只能打开现有 manifest 或补齐 v0.0 所需的最小目录，不改写 manifest；v0.0 命令范围内改写 manifest 只能通过 `loredock.repairProjectManifest`（带备份）执行，后续版本启用 capability 等写入走各自 preview/apply 和统一写入层。
- 示例空 capability 默认不写入用户 manifest；fixture 可以显式启用它来测试注册和卸载。
- `SafeFileWriter` 测试覆盖同目录临时文件、rename 替换、失败清理、未声明目录拒绝和路径/plan 校验边界。
- v0.0 diagnostics 使用 OutputChannel 和内存状态；diagnostics item 至少包含 `severity`、`code`、`message`、`workspaceFolder` 和可选 `relativePath`；激活、目标 folder 切换、manifest 写入和修复后刷新 diagnostics，`showDiagnostics` 重新打印当前 diagnostics，不把诊断结果作为 canon 写盘。
- diagnostics `severity` 只允许 `info`、`warning` 或 `error`。
- `loredock.openProjectManifest` 在 manifest 不存在时不会创建文件，只提示用户先运行 `loredock.initProject`。
- 文档明确写出：v1.0 前允许破坏式调整，v1.0 后才进入正式兼容期。
- 文档明确写出核心依赖方向：Kernel -> Capability API -> Feature Module；不能反向依赖。
- 有一个示例空 capability，证明后续模块可以注册和卸载，不需要改 Kernel 内部实现。
- Kernel 不 import 具体业务模块私有类型。
- `extension.ts` 可以作为 composition root 组装 capability，但 Kernel 私有实现不能依赖 feature module。
- 任意项目文件写入都经过统一 writer。
- 这个版本不包含手稿、资料库、AI、看板、时间线或导出功能。

## 风险

- 在没有真实功能前过度设计模块系统。
- 把简单问题藏进过厚的抽象层。
- 让未来功能假设提前污染 Kernel。
